---
name: documentation
description: Write or update documentation — README files, code comments, API docs. Use when the user asks to document something or write a README.
---

1. Write for someone who has never seen this project — state what it does and why it exists before how to use it.
2. A README needs, in this order: one-line description, how to install/run it, one concrete usage example, then anything else (config, architecture, contributing).
3. For code comments: only explain the *why* behind non-obvious decisions (a workaround, a constraint, a subtle invariant) — never restate what the code already says. If you're tempted to write "// increments counter" above `counter++`, don't.
4. Keep examples runnable and accurate — copy real commands/code from the project rather than inventing plausible-looking ones, and verify a code example actually matches the current API before including it.
5. Match the existing documentation style in the project (heading structure, tone) rather than imposing a new one.
